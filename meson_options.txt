# eBPF-based entropy source configuration
################################################################################

# Option for: ESDM_ES_SCHED_EBPF
option('es_sched_ebpf', type: 'feature', value: 'disabled',
       description: '''Enable support for eBPF-based scheduler entropy source.

The ESDM models an entropy source based on the timing of the
occurrence of scheduler-triggered context switches. In contrast
to the es_sched entropy source which requires a patched kernel,
this entropy source obtains the context switch timing by
attaching an eBPF program to the stable sched_switch tracepoint
of a stock Linux kernel (BTF/CO-RE required, i.e. the kernel
must be built with CONFIG_DEBUG_INFO_BTF).

In FIPS 140, SP800-90C and NTG.1 mode the event timestamps are
health-tested (SP800-90B RCT and APT) inside the eBPF program,
which collects the time between successive events of a CPU in
per-CPU buffers - the spacing of
the events is where the entropy is, and it is the signal the
SP800-90B assessment measures. A buffer is handed to a BPF ring
buffer once it is full, or after an idle deadline when its CPU
falls quiet before that. The ESDM server reads them from there
when it wants entropy, conditions them into an entropy pool - an
XDRBG-256 over SHAKE256 like the auxiliary pool - and stops
reading once that pool is full.
Events collected while nobody reads are discarded.

This entropy source is mutually exclusive with the es_sched
and es_irq entropy sources with respect to entropy crediting:
at most one of the scheduler/interrupt-based entropy sources
may have an entropy rate greater than zero.

The BPF programs are loaded during the privileged
initialization phase of the ESDM server (root or
CAP_BPF + CAP_PERFMON required). The server operates their maps
after it dropped its privileges, which Linux before 5.19 only
permits with kernel.unprivileged_bpf_disabled = 0: the entropy
source checks for it and disables itself where it does not hold.
''')

# Option for: ESDM_SCHED_EBPF_ENTROPY_RATE
option('es_sched_ebpf_entropy_rate', type: 'integer', min: 0, max: 256,
       value: 0,
       description:'''eBPF scheduler-based entropy source entropy rate.

The option defines the amount of entropy the ESDM applies to 256 bits of
data obtained from the eBPF scheduler entropy source. Every context switch
event contributes the 64 bit delta of its time stamp to the previous one, so
256 bits of data are four events. The ESDM enforces the limit that this value must be between 0 and
256 bits.

The credited entropy is additionally capped by the oversampling rate
(es_sched_ebpf_osr), which states the assessed min-entropy of one event.

The default of 0 means the entropy source is not credited with any
entropy until the entropy rate of the deployment environment has been
measured with the es_ebpf_testing support and a suitable rate has been
determined.

Note: The events for the interrupt-based and scheduler-based entropy
sources have dependencies. Thus it is not permissible to award more than
one of the es_irq, es_sched, es_irq_ebpf and es_sched_ebpf entropy
sources an entropy rate greater than zero.
''')

# Option for: ESDM_SCHED_EBPF_OSR
option('es_sched_ebpf_osr', type: 'integer', min: 1, max: 256, value: 1,
       description:'''eBPF scheduler-based entropy source oversampling rate.

The option defines the oversampling rate the SP800-90B health tests of the
eBPF scheduler entropy source are parameterized with: the tests assume a
min-entropy of H = 1 / OSR bits per event, i.e. OSR events are required per
bit of entropy. It determines the RCT and APT cutoffs applied inside the
eBPF program.

Set it from the min-entropy measured with the es_ebpf_testing support:
OSR = ceil(1 / H), rounded up so that the cutoffs are never less strict
than the measurement warrants. The value must be consistent with
es_sched_ebpf_entropy_rate: as 256 bits of data are four events, a rate of
4 / OSR bits per 256 data bits is the most the assessment supports. The
accounting caps anything above that and the server logs a warning.

The default of 1 is the strictest setting (one bit of entropy per event)
and matches the shipped entropy rate of 0, which credits no entropy at all.
''')

       description: '''Build the fuzz harnesses in tests/fuzz.

The harnesses drive the RPC interfaces with attacker-controlled bytes: the
requests the server takes off its two sockets, the responses a client parses,

a buffer to the request and response handling without a connection behind it,
